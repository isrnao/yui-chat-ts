## 1. 対象・状態の所有者・設計原則

対象はトップ、通常チャット、全部屋まとめ、Chanari、404、共通部品、停止中のツーショット専用画面、およびF01〜F11の追加予定インタラクション。表示上の装飾、キーボード、タッチ、非同期処理、エラーからの復帰まで含める。ツーショットは`TWO_SHOT_CHAT_ENABLED = false`で、現在の`/chat/2shot/`・`/chanari/2shot/`は公開の通常部屋として扱う。専用画面の計画を理由にflagを変更しない。

| 所有者             | 持たせる状態・処理                                                                                    | 実装時の契約                                                                                                                            |
| ------------------ | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| HTML / ブラウザ    | フォーカス、hover・押下、入力制約、単純な開閉、フォームの値                                           | `button`・`a`・`form`・`dialog`・`details`・`select`・radio・checkboxを意味に合わせて使う                                               |
| CSS                | 状態に応じた配色、選択強調、配置、レスポンシブ、短い遷移                                              | `:focus-visible`・`:focus-within`・`:checked`・`:user-invalid`・`:has()`、Container Queries、必要ならAnchor Positioningで表示を導出する |
| React / アプリ層   | 入退室、投稿・削除・通報、返信先、取得結果、pending/error、保存設定、読書位置、ユーザーが調整した寸法 | データ・副作用の単一の所有者を保つ。DOM状態を装飾のためだけにbooleanへ複製しない                                                        |
| 小さな互換・同期層 | dialogの命令未対応、popoverの機能確認、業務処理開始・終了とDOMの同期                                  | 機能単位で検出し、ネイティブ操作とfallback操作を同じクリックで二重に実行しない                                                          |

- 「stateの個数を減らす」こと自体を目標にしない。投稿に必要な値や保存設定は保持し、開閉の真偽だけを整理する。
- 開閉とデータ対象を分ける。例: 通報対象UUIDはReact、dialogの開閉はブラウザ。対象を閉じた後に消すための`close`イベント連携は必要であり、表示用stateの再導入とは区別する。
- 現行はMPA。部屋移動は実URLの`a href`、ページ内操作は`button`とする。CSSタブや`:target`で投稿先・ランキング取得を制御しない。
- Reactの`Activity`、`useActionState`、`useOptimistic`、`useSyncExternalStore`、React Compilerを維持する。ネイティブ化のために新しいUIライブラリ、Custom Elements、汎用の状態管理ライブラリを導入しない。
- SSG時も同じ意味のHTMLを出す。描画中に`window`や対応機能から別マークアップを選ばず、CSSによる初期表示と、hydration後のイベント時の機能検出を使う。

### dialogへの移行契約（C02 / C03 / C12）

1. `dialog open`をJSXで付けるだけでは非モーダルになる。通常経路は`showModal()`または`command="show-modal"`を使い、手動focus trapを併用しない。
2. 「キャンセル」「閉じる」だけは`method="dialog"`でよい。通報送信・フィルタ確定・削除はアプリ側の処理を成功/受理条件に合わせて実行し、単に`returnValue`を設定しただけで実行済みと扱わない。非同期送信フォームと取消フォームを入れ子にしない。
3. 既存の背景クリックによる取消は維持する。`closedby="any"`は機能を別途検出し、未対応時はdialog外でのpointerdown/upの両方を確認する小さなfallbackだけを置く。開いた操作の互換click・dialog内から外へのドラッグでは閉じない。
4. `cancel`、`close`、明示的な完了を一つの終了経路へまとめる。確認→通報は前のdialogを閉じてから次を開き、二重modal/復帰フォーカスの競合を防ぐ。フィルタで起点行が消える場合、代替フォーカス先を先に決める。
5. 常設dialogはDOMと表示内容のsnapshotを保持して退出transitionを可能にする。`close`でアクティブな業務対象を解除しても、表示snapshotは次回openまで残して退出中の空白化を防ぐ。新しい対象は次回openの前に設定する。退出待ちタイマーは使わず、StrictModeの再実行・unmountでは安全に閉じる。
6. ポータルはoverflow回避のためだけなら不要になる。共通部品として残す場合は所有ルートを明示し、`Activity hidden`による非表示と開いたTop Layerの取り残しを検証する。ランキング切替/退室ではそのビュー所有のpopup/dialogを先に終了する。

### フォーム値の移行契約（C04 / C06 / C07 / C11 / C12 / N02 / N04）

ブラウザが保持する値を`FormData`で読む案は、保存先・復元・即時previewに不要な局所値から適用する。controlled/uncontrolledを途中で切り替えない。前回設定のhydration後復元、入室失敗によるフォーム再mount、リセット時の保存設定更新があるidentity/アバターは、単純な`defaultValue`置換で解決したことにしない。送信中にスタイル欄を変更できる現行画面では、送信開始時のmetadataを一つのsnapshotとして保持する。クライアントの制約検証はサーバー検証の代わりにならず、予約名・URL兼用・trim・投稿コマンドの規則を既存共有ルールと揃える。

取消buttonが送信フォームに属する場合は`formNoValidate`または`type="button"`の閉じる命令を使い、必須radioや空のWordPickerが取消を妨げないようにする。通常発言は即時clearを維持しつつ、送信開始時の本文を保持する。失敗時は新しい入力がなければ本文を戻し、新しい編集があれば上書きせず「送信できなかった本文を戻す」操作を出す。clear/cut等のコマンドは本文回復と別に扱う。IMEのcomposition中はEnter確定を送信として扱わない。

入室はルート/sessionが処理中の要求を一つだけ受け付け、フォームのpending表示と整合させる。現行の即時入室表示を維持する場合も、失敗復帰時に入力値とエラーが戻り、未完了要求が別の入室へ結果を返さないようにする。`showFilter`のような開閉専用booleanは主状態にしないが、開いている間だけ重い件数計算を有効にするためのDOMライフサイクル由来の補助状態は許容する。開いた直後と、その後のログ/store更新の両方で一覧の件数が最新になる契約を保つ。

### 13.3. 初回計画を具体化・修正した点

- C12で開閉booleanを削ることと、重い件数計算を必要な間だけ有効にすることは両立させる。DOMのopen/toggle/closeから計算用snapshotを更新する補助状態は許容し、render中にrefを読んで状態管理を代替しない。
- CSSのcascadeも再点検し、T05の通常`all:revert`がタッチ文字サイズの`!important`まで消すとした前提を訂正した。C10の共有popoverでもinvoker関係は維持でき、portalの祖先関係と暗黙anchorを同じ条件として扱わない。
- CSSの`display:none`・`:has()`は業務状態やAPI成功を表さない。A01/A02/A03/A07の状態を「CSS化できるboolean」として削減対象にしない。
- 表示だけのChanari項目は初回N03の方針を維持する。今回の追加検討でエフェクト/ATの実動化や本文装飾metadataの拡張を追加しない。
- A04の全部屋projectionと論理削除行の取得範囲は別の責務。通常部屋の取得条件を全画面へ一律適用して、全部屋の既存仕様を壊さない。削除の意味を変える場合は機能仕様の改訂へ分ける。
- 初回C08のActivityによるログ/読書位置の保持と、A09のroute identity変更による初期化を区別する。ランキングを開くたびにsessionやログstoreを再作成しない。
- A11の期限確認はdomainの復元/復帰イベントで行い、`getSnapshot()`が時刻だけで新しいobjectを返す変更を避ける。debounceは入力が必要なdraft保存に限り、送信順序やフォーカスを遅延させない。
- R0の試作を全改善の前提にしていた依存を見直す。壊れたリンク・選択範囲・既存splitter・非同期例外・session境界は現在のUIのまま先に改善できる。実装順の最新版は14章を優先する。

- 既存の41項目を別文書へ移管し、状態の所有者・互換対応・受け入れ条件を維持した。元の機能計画には参照リンクだけを残し、文書内の章番号と機能計画への参照を区別した。
